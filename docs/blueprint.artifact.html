Crystalina blueprint

What Crystalina is, what actually runs today, and the move to Cloudflare that turns two half-deployed hosts into one. Every drawing in this document is generated from one data file, and every status word on every card is one of five.

Prepared 2026-10-09 State verified 2026-10-09 (hosting), 2026-08-31 (database) Target Cloudflare Pages, Pages Functions and Turnstile, with Supabase kept for data and identity

2026-10-11 — the drawings were rebuilt on an orthogonal router, so every arrow now leaves a named side of a card and turns at right angles rather than curving across the page. Content unchanged since 2026-10-09, when the blueprint was first written and the hosting facts were checked against the live hosts.

1Executive summary

Crystalina is a premium home water filtration shop for New York City: thirteen products, a catalogue with real compatibility and bundle relationships, a customer account, and four staff workspaces for admin, managers, sales and field technicians. The design is built. The database is built and protected. What is missing is the middle: one host that actually runs the server code, and a way to take money.

The five findings that matter

FindingSeverity
1Two hosts serve one project and neither serves it completely. crystalina.org is GitHub Pages, which cannot run the /api folder at all; the Vercel copy runs it but has no environment variables, so every server call returns 500. Re-checked 2026-10-09: still true, six weeks after it was first written down.Critical
2Nothing takes payment. There are zero Stripe references in the codebase, and the checkout button is disabled on purpose so that nobody can place an unpaid order. The shop cannot open until this exists.Critical
3The dashboards are gated in the browser. Row level security protects the data, which is the part that matters, but staff text reaches another staff member through innerHTML unescaped. That is a live stored-XSS route.High
4The catalogue is schema-complete and data-empty. Stock is 0 on all thirteen items, product_stage_options has no rows, and no faucet products exist, so the shop reads as sold out and the five, six and seven stage choice never renders.High
5The accounts that would bring people in already exist and are not connected. The domain, Google Search Console, the Meta Business account and the WhatsApp number are all held; there is no product feed, no analytics and no attribution on any of them.Medium

The path, in four lines

  1. Move to Cloudflare. One account serves the pages, runs the server code, holds the captcha, gates the preview and rate limits the API. That retires both current hosts and removes the whole class of problem in finding 1.
  2. Build the payment path once, carefully, with the money recomputed on the server and the webhook keyed so a retry cannot charge twice.
  3. Close the security findings while the site is still small: escape the dashboards, put the Turnstile widgets on the forms, move the rate limit to the edge.
  4. Then seed the catalogue, point the DNS, and open.
What this document is

Not a proposal and not a snapshot that stopped being true in week two. Every decision below carries a number, a date, what it costs and when it should be replaced. Every unknown carries an owner and what it blocks. When a decision changes, this file changes in the same commit as the code.

The shape of the problem

The repository is correct. Both deployments are correct in isolation. What is wrong is that the domain points at the half that cannot run code, and the half that can run code has never been given its keys. No amount of further building fixes that; one deployment decision does.

What is genuinely finished

  • The design system in css/styles.css: palette, type, the unified button, the components. Every page is assembled from it.
  • The storefront: home, shop, product, quiz, NYC water, about, contact. All hydrate from Supabase where they should.
  • The database: 23 tables with row level security, a server-authoritative create_order that reprices every line and decrements stock in one transaction, and four staff-gated catalogue functions that correctly refuse anonymous callers.
  • The server boundary itself: three functions with method guards, body size caps, input cleaning, Turnstile verification and an order path that never trusts a browser-supplied price.
  • Twenty tests, all passing, run on 2026-10-09.

What looks finished and is not

  • The shop. Every product renders, and stock is 0 on all thirteen, so a visitor sees a catalogue of sold-out items.
  • The product page. The five, six and seven stage choice and the faucet upgrade are both built and both have no data behind them, so neither control appears.
  • Checkout. The whole order path works except the part that takes money, and the button is disabled so that the gap cannot be reached by accident.
  • The contact and newsletter forms. They validate, they are rate limited, they verify a captcha, and in production they return 500.
  • Sign-in. Real Supabase Auth on /signin/ only. The other five pages that need a session still read local state, and the old Store.signUp and Store.signIn stubs are still exported.

3The move to Cloudflare

One platform for the pages, the server code, the captcha, the preview gate and the rate limit, with the database left exactly where it is. This is the smallest change that removes the largest problem.

What moves, and what deliberately does not

JobTodayAfterWhy
Serving the pagesGitHub PagesCloudflare PagesStatic files served from the edge, and the same project can run server code. One host instead of two.
Server codeVercel functionsPages FunctionsThree routes, already dependency free and already written against the standard fetch and crypto APIs. The port is small.
DNSSquarespaceCloudflare DNSThe zone has to be on Cloudflare for Access, WAF rules and Web Analytics to apply. The registrar can stay where it is.
CaptchaCloudflare TurnstileCloudflare TurnstileAlready the choice. It simply comes home to the same account and dashboard.
Rate limitingAn in-process counterWAF rate limiting on /api/*A counter inside a serverless instance does not survive the instance. The edge is the only place this can be true.
Preview protectionNoneCloudflare AccessA staging site that a search engine can index is a known hazard. Access closes it, free, including on the pages.dev address.
Database, auth, storageSupabaseSupabase, unchangedSee AD3. Moving to D1 would be a rewrite of everything that currently works.
AnalyticsNoneCloudflare Web AnalyticsNo cookie, so no consent banner, so no third thing to build.
The rule that survives the choice

Two environments, secrets per environment, a deploy that is one command and a rollback that is one more. Cloudflare Pages gives all four. If a platform ever makes one of them hard, that is the signal to look again rather than to work around it.

What the owner does, and what the agent does

  1. The owner creates the Cloudflare account and turns on two-step sign-in.
  2. The owner creates a scoped API token with Pages edit permission, and stores it with the account id as repository secrets. The agent never sees a password.
  3. The owner adds every secret in section 10 to the Pages project, per environment. The agent names them; it does not hold them.
  4. The owner moves the crystalina.org nameservers to Cloudflare when, and only when, a preview has passed.
  5. The agent does everything else, and lists in a handoff exactly which names were set and which were not.

Architecture after the move to Cloudflare. One platform serves the site and the server boundary, and one DNS zone sits in front of both. Supabase is kept: the schema, the row level security and the server-authoritative order function already exist and work, and moving them to D1 would be a rewrite with nothing to show for it (AD3). Turnstile is already the captcha, so it comes home to the same account. Open on its own

4Channels and accounts already held

Crystalina is not a new project, so most of the "go and open an account" work in a normal build is already done. The domain is owned, Search Console is verified, the Meta Business account exists, and the WhatsApp number is live and linked from every page. The question for each one is not whether it exists; it is whether the site actually uses it, and whether the move breaks it.

Channels and accounts already held. The domain, Search Console, the Meta Business account and the WhatsApp number exist. The status on each card is whether the site actually uses it. Open on its own

What the move must not break

  • Google Search Console is verified by a file served at /googlea4ca9585bd44aaf9.html. That file has to keep being served from the root on the new host, or verification lapses silently. Once the zone is on Cloudflare, adding the DNS TXT method as a second, host-independent proof costs nothing and is worth doing.
  • sitemap.xml lists seven URLs and no dates. It is missing /product/ and /checkout/ and has no lastmod on any entry. Worth fixing in the same change as the cutover.
  • The WhatsApp link is a plain wa.me link, so it is unaffected by hosting. It appears in the footer, in the hero and as a floating button on every page.
  • The footer social links and the schema.org sameAs list in index.html both name the same four profiles, in two places. That is a second copy; see section 13.
The gap worth naming

Three accounts that are held and unconnected: there is no product feed for Google Merchant Center or the Meta catalogue, no analytics of any kind, and no Meta Pixel or Conversions API. Thirteen products with no feed is free traffic left on the table, and a pixel added after an ad campaign starts cannot report on the days before it. None of this blocks launch, and all of it is cheaper to decide now than to retrofit. Note that adding a pixel also turns the cookie banner into a real question; Cloudflare Web Analytics on its own does not.

5The content model

Twenty three tables in one Supabase project, grouped by what they are for. The fields shown in the drawing are the ones another part of the system depends on, not every column.

The content model. What exists in Supabase, which tables are still empty, and where the privilege boundary sits. Open on its own

The privilege boundary

  • The browser holds the publishable key only. Every read it makes passes row level security, and the key is safe in public for exactly that reason and no other.
  • Every privileged write goes through /api with the service role, or through a security definer function gated on private.has_role(). There is no third path.
  • Prices, totals and stock are recomputed in the database. The browser sends ids and quantities and never money. create_order prices stage options and faucet upgrades server-side, so the payment work in phase 3 reuses it rather than recalculating anything in JavaScript.

Migrations

Additive and re-runnable: create or replace, if not exists, drop-then-create for policies. Forward only, numbered, applied as a job rather than by hand. Keep it that way: a migration that cannot be run twice will eventually be run twice.

Deliberately accepted

The security headers in vercel.json (nosniff, strict referrer, DENY framing, a closed permissions policy, HSTS with preload) are carried over unchanged to Cloudflare as a _headers file. There is no Content-Security-Policy yet: the pages use inline handlers in places, so a policy added today would either break them or be weak enough to be theatre. It belongs with the XSS sweep in phase 6, not before it.

8Performance budget

The targets are set. The bars are empty, because nothing has been measured on a served copy yet, and a guessed number in a budget is worse than an empty one: it gets believed. scripts/verify.mjs reports transferred weight per page and fills these in.

Performance budget. The targets are set. The bars stay empty until the harness has rendered a served copy, because a guessed number in a budget gets believed. Open on its own

  • The site is static HTML, CSS and JavaScript with no build step, so there is no bundler cost to argue about and no framework runtime to pay for.
  • Imagery is the whole budget. The hero is allowed to be the single heaviest asset on the site; everything below the fold is lazy.
  • Cache busting is not in place. Styles and scripts are referenced without a version or a hash, so a returning visitor can hold a stale stylesheet after a deploy. This is almost always the cause when a site "looks broken" for some people and not others, and it is worth fixing with the Cloudflare move rather than after it.

One deploy path, not two

Cloudflare Pages can deploy from its own Git connection or from a workflow in the repository. Pick one. With both connected, every push deploys twice, the two deployments race, and the one that wins is whichever finished last. The workflow is the choice here, because the tests and the render harness have to pass before anything is published.

Rollback

Promoting the previous Pages deployment, which takes seconds. It has to be practised once, deliberately, before launch, by someone who is not the person who built it. A rollback nobody has run is a rollback nobody can run at two in the morning.

15Architecture decisions

Numbered, dated, never renumbered. The last two lines of each are the ones people skip and the ones that matter in a year.

AD1 Cloudflare Pages and Pages Functions, rather than staying on Vercel or on GitHub Pages 2026-10-09

What it does
One project serves the static pages and runs the three server routes, behind one DNS zone we control.
Why we need it
Today the domain points at a host that cannot run server code, and the host that can has never been given its keys. Any fix that leaves two hosts in place leaves the same confusion.
Why it belongs here
Turnstile is already the captcha and is a Cloudflare product. Access closes the preview for free. WAF rate limiting fixes a security finding that cannot be fixed in application code. Web Analytics needs no cookie and therefore no consent banner. All four come with the zone.
What it costs
A nameserver move, a port of three functions from the Node request and response style to the Workers fetch style, and a runtime that is not Node, so every library has to be checked. There are no libraries: the functions are dependency free.
Right for now
Three routes and a static site sit far inside the free plan. Workers Paid at five dollars a month is the ceiling, not the floor.
Replace when
The server work grows beyond what a Pages Function can do inside its CPU limit, or a long-running job appears that wants a real Node host.

AD2 Pages Functions rather than a Worker with a framework 2026-10-09

What it does
Each route stays one file under functions/api/, matching the existing /api layout one to one.
Why we need it
The three routes are already written against standard web APIs and have no dependencies. They need a runtime, not a framework.
Why it belongs here
The site has no build step, and adding one to serve three endpoints would be the largest change in the project for the smallest reason.
What it costs
No file-based routing conveniences, and the Node request and response shim has to be written once and tested.
Right for now
Three endpoints. A framework earns its place somewhere around twenty.
Replace when
The server surface grows past roughly a dozen routes, or server-rendered pages become necessary.

AD3 Supabase stays. The data does not move to D1 2026-10-09

What it does
Postgres, row level security, Auth and Storage stay exactly where they are. Only the serving layer moves.
Why we need it
Twenty three tables, twelve applied migrations, policies on every table, a server-authoritative order function and four staff-gated catalogue functions already exist and work.
Why it belongs here
D1 has no row level security. Moving would mean reimplementing every policy as application code behind a data access layer, with a test for every path, to gain a network hop. The security model is the most valuable thing in the project.
What it costs
A network hop from the Worker to Supabase, a second vendor, and a bill that grows with use.
Right for now
The database is nowhere near being the bottleneck, and the policies are the reason the browser can safely hold a key at all.
Replace when
The Supabase bill becomes material, or the latency of that hop shows up in a measurement rather than in a worry.

AD4 The money is recomputed in the database, and the webhook is the source of truth 2026-10-09

What it does
The browser sends product ids and quantities. create_order prices every line, including stage options and faucet upgrades, checks stock and decrements it in one transaction. The Stripe webhook, not the browser redirect, marks an order paid.
Why we need it
A price that the browser can influence is a price a customer can choose. A redirect that the browser can skip is a payment that can be lost.
Why it belongs here
Half of it already exists and is tested. The payment work extends it rather than inventing a parallel path.
What it costs
The webhook has to verify its signature and be keyed on the event id, because Stripe will redeliver.
Right for now
This is the one flow that has to be right the first time. Being taken twice for the same order is not something you can apologise your way out of.
Replace when
Never, as long as the site takes money.

AD5 Every diagram is generated from one data file 2026-10-09

What it does
docs/diagrams/model.mjs holds the system as data. scripts/diagrams.mjs draws every SVG from it, and this document is generated too. Nothing is hand placed.
Why we need it
A status picture that is two weeks old is worse than none, because it is believed. Hand-drawn diagrams are never updated after the second time.
Why it belongs here
The site map with a status on every page is the one picture that answers "how far along are we", and it is read by whoever is paying rather than by whoever is building.
What it costs
A renderer to maintain, and layout expressed as code rather than dragged into place.
Right for now
Fifteen drawings from one file, regenerated in under a second, with npm run diagrams:check failing a pull request where the picture and the model disagree.
Replace when
The drawings need art direction that layout code cannot express. Then export once to a design tool and accept that it is now a second copy.

AD6 Icons are symbols, and diagram elements are components 2026-10-09

What it does
Every icon is one SVG symbol, instanced with use. Every repeated diagram element (the card, the zone panel, the page card, the table card, the sequence lane, the note panel, the connector) is one component in scripts/lib/components.mjs, with its variants listed in a manifest.
Why we need it
It is the same rule the site runs on, applied to the drawings. An icon copied into three diagrams is three icons to fix.
Why it belongs here
It is also what makes the set exportable: a symbol library and a component manifest map one to one onto a design tool's components and instances, so the set can be rebuilt in Figma without being redrawn.
What it costs
Layout maths lives in code, and a component change redraws everything, which is the point and is occasionally startling.
Right for now
Forty one symbols and six components carry sixteen drawings, and the library sheet in section 18 shows every one of them.
Replace when
The library is maintained in a design tool and exported into the repository, rather than the other way round.

AD7 The site is published from an explicit allow-list, not from the repository root 2026-10-09

What it does
npm run build:site copies a named list of directories and files into dist/, refuses to finish if anything on a forbidden list made it in, and writes a manifest. Pages publishes dist/.
Why we need it
Serving the repository root publishes the repository. Verified on 2026-10-09 against the live Vercel host: the SQL migrations, the test files and the internal task list were all downloadable by anyone.
Why it belongs here
Cloudflare Pages has no special case for /api, so without this it would publish the server source as well. The move forces the question, which is the good time to answer it.
What it costs
Adding a file to the site means naming it in one list. That friction is the feature.
Right for now
Fifteen directories and nineteen files. Small enough to read in one screen.
Replace when
A real build step appears for another reason, and can own the same list.

AD8 Montserrat for text, and a Canela-like serif for titles 2026-10-09

What it does
Replaces Inter and Poppins across the site and the blueprint. Two tokens in css/styles.css and one in scripts/lib/tokens.mjs.
Why we need it
The brand reads as a premium product and was set in two geometric sans faces, which read as a technology product.
Why it belongs here
Changing it costs two tokens and a font link while the site is pre-launch. After launch it is a visual regression test across every page.
What it costs
Montserrat is a wider face than Inter, so anything that was close to wrapping now wraps. Checked at 1280: the navigation still fits on one line. Canela is licensed, so Playfair Display stands in for it.
Right for now
Both faces are on Google Fonts, so there is no licence to buy and no file to self-host yet.

Canela is licensed. Then change the one token in each place, and self-host rather than loading from a third party.

17The drawing system

Every drawing in this document is assembled from one icon library and six components, and coloured by a six-family palette where the colour carries meaning rather than decoration. This section is the key to reading all of them.

What the colours mean

FamilyStands for
BlueThe visitor, and anything a customer touches
AmberThe edge: hosting, DNS, caching, the things in front
VioletIdentity, secrets, anything that proves who someone is
TealData at rest
GreenMoney, and the things that must be exactly right
RoseDanger, failure paths, and anything untrusted
SlateNeutral, and anything deliberately postponed

A status word is a family too, so Partial is the same amber on a card, in a table and in a progress report. The word is printed on every chip as well as the colour, and anything that does not exist yet also carries a dashed outline, so a monochrome printout and a colour-blind reader both lose nothing. An arrow takes the colour of what it points at, which means a path through a drawing can be followed by colour alone.

18How this document is kept true

  • The source is docs/blueprint-content.mjs and docs/diagrams/model.mjs. Three surfaces are generated from them and none is written by hand: the Artifact at https://claude.ai/artifact/SrRGRwrLYrSisyGC53rCLo, which is the one to send anybody; docs/blueprint.html, the same page as a file that opens from the repository; and docs/blueprint.md, for reading in a pull request. Editing any of the three is work that the next regeneration silently destroys.
  • npm run blueprint rebuilds all three. npm run diagrams rebuilds every drawing. npm run check runs the tests, the publish allow-list and both drift checks, so a stale picture or a page that has drifted from its source cannot survive a pull request.
  • Amend this in the same commit as the change it describes. A decision that changes in code and not here is a decision that will be made again, differently.
  • Mark an answered question answered, with the date and the answer. Do not delete it.
  • When a section is superseded, say so at the top of the section and point at what replaced it. Never renumber.
  • Two assistants commit to main. Read COORDINATION.md before editing, and pull before you start and before each push.
Publish from one place

The Artifact is published from this repository and nowhere else. Anyone republishing it pulls first and republishes to the same URL (https://claude.ai/artifact/SrRGRwrLYrSisyGC53rCLo) rather than creating a second one.
